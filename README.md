# Homework Publisher

Telegram-бот для публикации домашних заданий с 1–10 фотографиями в канал.
Работает на Telegram Serverless, использует только SDK из [справочника](docs/tgcloud-sdk.md).
Локальный сервер и npm-пакеты в модулях бота не нужны.

## Настройка

В `tgcloud/lib/config.js` перед отдельным развёртыванием заполните:

- `allowedUserIds`: массив **числовых** Telegram ID редакторов. По умолчанию пуст — доступ закрыт всем. Username не используется для авторизации.
- `channelId`: ID канала строкой `-100…` или публичный `@username`. Бот должен быть администратором этого канала с правом публикации сообщений.
- `types` и `subjects`: варианты на кнопках. Их можно изменить под расписание школы.
- `utcOffsetMinutes`: по умолчанию `180` (Москва). Допустима дата от сегодняшней до даты через год включительно.

Это публичные идентификаторы и параметры, токены в код не добавляются.
`AGENTS.md` и `.tgcloud/` не изменялись; служебную папку нельзя читать или редактировать вручную.

## Использование

1. В личном чате с ботом отправить `/start`, нажать «Новое задание».
2. Выбрать тип, ввести дату `ДД.ММ.ГГГГ`, выбрать предмет.
3. Ввести название задания одной строкой (1–300 символов).
4. Отправить 1–10 фотографий **как фото**: по одной или альбомом. Дождаться получения всех фотографий. Бот показывает счётчик; при необходимости `/draft` показывает актуальное состояние и кнопки.
5. Нажать «Предпросмотр». Бот отправит фотографию или альбом с итоговой подписью в личный чат.
6. Нажать «Подтвердить публикацию». Одна фотография публикуется через `sendPhoto`, 2–10 — одним `sendMediaGroup`. Подпись ставится только к первой фотографии, без HTML/Markdown-разметки.

`/draft` и `/start` восстанавливают текущий шаг из БД. `/help` также показывает текущий шаг.
`/cancel` или кнопка отмены удаляют содержимое незавершённого черновика; после этого можно создать новый.
Для исправления полей до подтверждения отмените черновик и начните заново. В предпросмотре можно вернуться к фото и очистить их.
Редактирование уже опубликованных сообщений не реализовано.

## Сохранность и повторные запросы

`homework_drafts` содержит один текущий черновик на Telegram ID, состояние, монотонную ревизию и JSON полей/фотографий.
Кнопки привязаны к ревизии: старые кнопки не изменяют новый черновик. Запись использует атомарный SQL `UPDATE … WHERE revision = … AND state = …`.
Параллельные фотографии повторно применяются к свежей версии, поэтому не затирают друг друга. Повтор одного `message_id` и повтор фото по `file_unique_id` не добавляют фото второй раз. Сверх лимита фото отклоняются; файлы-документы не принимаются.

Перед обращением к каналу черновик атомарно блокируется в `publishing`, затем создаётся запись `homework_publications` с уникальным ID `TelegramID:ревизия`, содержимым и адресатом. Повторное подтверждение не отправляет публикацию ещё раз. Успех фиксируется вместе с ID сообщений. История сохраняется при создании следующего задания.

**Telegram API не предоставляет общей транзакции с БД и ключа идемпотентности для отправки сообщений.** После тайм-аута нельзя достоверно отличить неотправленное сообщение от отправленного. Поэтому при любой ошибке отправки или фиксации результата автоматический повтор запрещён: состояние `uncertain` либо оставшееся `publishing` блокирует также отмену и новый черновик. Это намеренный выбор в пользу отсутствия дублей, а не гарантия доставки.

Администратору нужно сверить канал, запись `homework_publications` и серверные логи по ID публикации. Нельзя просто повторять отправку или сбрасывать блокировку по таймеру. После ручной проверки через разрешённый инструмент работы с БД:

- Если публикация есть — зафиксировать в журнале `published` и фактические `message_ids`; у соответствующего черновика установить `published`, увеличив `revision`.
- Если подтверждено, что публикации нет — пометить журнал `not_sent`, перевести соответствующий черновик в `cancelled`, увеличить `revision`; пользователь создаст задание заново.
- Если результат всё ещё неясен — оставить блокировку.

Изменять нужно только проверенного пользователя и ожидаемую ревизию, условным обновлением. Перед ручным изменением убедиться, что исходный обработчик больше не выполняется. Существующий журнал не удалять. Если ошибка случилась до создания записи журнала, содержание остаётся в заблокированном черновике. Права на ручной разбор не выдаются через интерфейс бота.

## Локальная проверка

Требуется Node.js **24+** для тестов (`node:sqlite`, VM modules); сами модули бота не используют Node API.

```sh
npm ci
npm test
```

Тесты запускают исходные модули в изолированном VM-контексте, создают настоящую SQLite по экспортам схемы, подставляют имитацию `api` и проверяют в том числе параллельные запросы и сбои. Они не читают `.tgcloud/`, не используют сеть и ничего не отправляют в Telegram. Предупреждение об экспериментальных VM modules ожидаемо.

## Проверка после отдельного развёртывания

В этой задаче развёртывание и миграции не выполнялись. На своём компьютере сначала заполните конфигурацию и разверните код согласно `AGENTS.md`, затем отдельно примените миграцию схемы: push сам по себе БД не меняет. До готовности таблиц не используйте сценарий бота.

Для проверки возьмите отдельный тестовый канал, выдайте боту право публикации и временно укажите его в конфигурации. Проверьте:

- Разрешённый ID проходит весь сценарий; другой ID и групповой чат не получают доступа.
- Неверная/прошлая дата, пустое/длинное название, документ и 11-е фото отклоняются.
- `/draft` восстанавливает шаг и фото; повтор фото не увеличивает счётчик.
- Предпросмотр не публикует в канал; отмена и устаревшие кнопки не публикуют.
- Одна фотография и альбом из 10 фотографий доходят с правильной подписью; повтор подтверждения не создаёт дубля.
- При отсутствии права публикации появляется блокировка, которую администратор разбирает вручную.

Локальные тесты проверяют логику, но не подтверждают совместимость реального рантайма, права бота и успешность миграции. Эти проверки остаются для отдельного развёртывания.
